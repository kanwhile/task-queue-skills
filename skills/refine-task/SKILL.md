# Refine task

อ่าน `config.md` และ `trackers.md` ในโฟลเดอร์สกิลนี้ก่อน · config ไม่ครบ = หยุดตามที่ `config.md` บอก
session นี้มีเจ้าของนั่งตอบอยู่ ส่วน `/pick-task` ทำงานโดยไม่มีใครตอบ ทุกอย่างที่มันต้องรู้จึงต้องอยู่ในการ์ดก่อนเข้าคิว

**จุดเดา** = จุดที่ agent ที่มีแค่การ์ดกับ repo ต้องเลือกเองเพราะไม่มีคำตอบเขียนไว้: พฤติกรรมในกรณีขอบ · ข้อความที่ผู้ใช้เห็น · ทำแค่ไหนถึงพอ · ข้อมูลเก่าต้องทำอะไร · test ที่ seam ไหน · รู้ได้ยังไงว่าเสร็จ
การ์ด **ready** = จุดเดาเหลือ 0 · AC ทุกข้อตรวจได้ด้วย test หรือสิ่งที่เห็นบนหน้าจอ · มี seam · มีนอกขอบเขต · จบได้ใน PR เดียว

## เลือกการ์ด
- ได้ `<ref>` → ทำใบนั้น
- ไม่ได้ → อ่านการ์ดสถานะ `unclear` ตาม `trackers.md` ข้ามใบที่ติด role `ready-for-human` (§triage label) เรียงตาม Priority แล้วแสดงตาราง 10 ใบแรก: ชื่อ · Priority · เป็นการ์ด `ตัดสิน:` ไหม · มี `task.md` ไหม (pick-task เคยลองแล้ว)
  ให้เจ้าของเลือกใบที่จะทำรอบนี้ แล้วทำทีละใบตาม "ทำการ์ด"

## ทำการ์ด
1. อ่านการ์ดตาม `trackers.md` ให้ครบ รวม `## คำถาม` · `## รอเจ้าของตัดสิน` · ความเห็น · ไฟล์แนบ
   มี `task.md` (`grep -l "<ref>" <root>/.tasks/*/task.md`) ให้อ่านทั้งไฟล์ด้วย เพราะ pick-task จดสิ่งที่ลองแล้วและการตัดสินใจไว้ในนั้น
2. อ่านโค้ดและเอกสารของ repo ส่วนที่การ์ดแตะ (ไฟล์กฎ · glossary หรือ `CONTEXT.md` · ADR · test ที่มีอยู่) แล้วลิสต์จุดเดาทั้งหมด
   จุดเดาที่โค้ดหรือเอกสารตอบได้ ให้ตอบเองแล้วจดที่มา เจ้าของตอบเฉพาะสิ่งที่ repo ตอบไม่ได้
   seam: ใช้ seam ที่มี test อยู่แล้วก่อน เลือกจุดที่สูงที่สุดที่ test พฤติกรรมของการ์ดได้ ยิ่งน้อยจุดยิ่งดี
3. ขนาด: ต้องส่งเป็นหลาย PR (มีหลายพฤติกรรมที่ส่งแยกกันได้ หรือ AC เกินราว 7 ข้อ) → ข้อ 4 ถามแค่เรื่องที่กำหนดทิศทาง แล้วจบใบนี้ด้วยผล **ใหญ่**
4. ถามจุดเดาที่เหลือด้วย `AskUserQuestion` วางตัวเลือกที่แนะนำไว้บนสุดและต่อท้าย `(แนะนำ)` · ทุกตัวเลือกบอกผลที่ตามมา
   - ย้อนยาก หรือแตะข้อมูล สิทธิ์ ความปลอดภัย หรือทิศทาง product → ถามทีละข้อ
   - เลือกผิดแล้วแก้ทีหลังได้ → รวมถามครั้งละไม่เกิน 4 ข้อ
   คำตอบเปิดจุดเดาใหม่ให้ถามต่อ · จบข้อนี้เมื่อจุดเดาเหลือ 0 หรือเจ้าของบอกว่าข้อที่เหลือต้องถามคนอื่น (ผล **รอข้อมูล**)
5. ร่างสิ่งที่จะเขียนตาม "รูปแบบที่เขียนลงการ์ด" แสดงให้เจ้าของดูทั้งก้อน แก้จนเจ้าของ OK
6. เขียนลงการ์ดและตั้งผลตาม "ผลของการ์ด" · จบใบนี้เมื่อการ์ดบนบอร์ดมีสเปก label และสถานะตรงกับผลแล้ว

การ์ด `ตัดสิน:` ใช้ข้อ 1 แล้วถามตามตัวเลือก ก/ข/ค ที่เขียนไว้ในการ์ด · เห็นด้วยกับทางที่ implement แล้วทุกข้อ → บอกเจ้าของว่าปิดการ์ดได้ ไม่ต้องเข้าคิว · ขอเปลี่ยนข้อไหน → เขียนคำตอบลงการ์ดแล้วตั้งผล **ผ่าน**

## ผลของการ์ด
ติด label (ตาม `trackers.md` §triage label) ก่อนเปลี่ยนสถานะ เพื่อให้การ์ดเข้าคิวพร้อม label เสมอ

| ผล | เขียนอะไรลงการ์ด | role | สถานะ |
|---|---|---|---|
| **ผ่าน** | สเปกจากข้อ 5 ตาม "แก้สเปก" ใน `trackers.md` · มี `task.md` ให้เขียนคำตอบลง "โน้ตจากเจ้าของ" ด้วย เพราะ pick-task รอบหน้าทำต่อจากไฟล์นั้น | `ready-for-agent` | `queued` |
| **รอข้อมูล** | คำตอบที่ได้แล้ว + คำถามที่เหลือใต้ `## คำถาม` พร้อมว่าต้องถามใคร | `needs-info` | คง `unclear` |
| **คนต้องทำ** | เหตุผลบรรทัดเดียว | `ready-for-human` | คง `unclear` |
| **ใหญ่** | ทิศทางที่ตกลงในข้อ 4 | ไม่แตะ | คง `unclear` |

ผล **ใหญ่**: บอกเจ้าของให้พิมพ์ `/to-spec` แล้วตามด้วย `/to-tickets` ต่อใน session นี้ เพราะ `/to-spec` สรุปจากบทสนทนา ทุกคำตอบที่ได้ในข้อ 4 จึงไปอยู่ในสเปก

## รูปแบบที่เขียนลงการ์ด
ใช้ภาษาเดียวกับการ์ด · เนื้อเดิมของเจ้าของคงไว้ · หัวข้อที่มีอยู่แล้วให้แก้ในที่เดิม แต่ละหัวข้อมีที่เดียว
```
## AC
- [ ] <พฤติกรรมที่ตรวจได้ 1 ข้อ: ทำอะไร → เห็นอะไร>
## seam
- <seam>: <test AC ข้อไหนที่นี่>
## การตัดสินใจ
- <ตัดสินอะไร> เพราะ <เหตุผล> (เจ้าของ <วันที่> | จาก <ที่มาในโค้ดหรือเอกสาร>)
## นอกขอบเขต
- <สิ่งที่การ์ดนี้ไม่ทำ>
```
`## คำถาม` ที่ตอบครบแล้ว: ใส่คำตอบใต้แต่ละข้อ แล้วเปลี่ยนหัวเป็น `## คำถาม (ตอบแล้ว <วันที่>)`

## จบรอบ
ตารางทุกใบที่ทำรอบนี้: ชื่อ · ผล · จำนวนข้อที่เจ้าของตอบ · ใบที่ผ่านแล้วรอ `/run-task-queue` หยิบ
